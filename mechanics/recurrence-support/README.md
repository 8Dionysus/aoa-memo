# Recurrence Support Memo Mechanic

Recurrence support is the memo-side mechanic for preserving bounded relaunch
anchors, witness trace exports, and reviewed closeout recall landings so OS
Abyss routes can return without turning `aoa-memo` into router, runtime, role
policy, proof, or a second route ledger.

## Mechanic card

- Status: `landed`

### Operation

preserve bounded relaunch anchors, witness trace exports, and reviewed closeout recall landings so routes can return without memo becoming router, runtime, role policy, proof, or a second route ledger

### Trigger

Use when a route needs memo-owned recurrence support: checkpoint continuity,
compact relaunch anchors, witness trace export posture, or a reviewed closeout
recall landing that should remain visible for later work without granting
dispatch, retry, role, proof, runtime, or owner-acceptance authority.

### Memo owns

Memo owns reviewable relaunch anchors, checkpoint-support posture, witness trace
mapping into existing memory objects, closeout recall landing posture, source
refs, provenance links, and stop-lines that keep recurrence support bounded.

### Stronger owner split

- `Agents-of-Abyss` owns recurrence doctrine, program law, and center route
  meaning.
- `aoa-agents` owns actor identity, role rights, handoff permissions, and retry
  authority.
- `aoa-playbooks` owns scenario choreography, campaign return posture, and
  reviewed closeout play.
- `aoa-sdk` owns dispatch behavior, tier escalation, route compression, and
  return navigation policy.
- `abyss-stack` owns live stores, runtime rebuild policy, retry loops,
  checkpoint workers, and return-event logging.
- `aoa-evals` owns proof, scoring, quality gates, and adoption verdicts.
- Source owner repositories own acceptance of the memory candidate or route
  consequence.

### Inputs

Inquiry checkpoint refs, recall contract refs, return packs, witness trace
exports, reviewed closeout carry, closeout handoff refs, owner-local recall
candidates, evidence refs, memory delta refs, route-return hints, and stronger
owner feedback that a relaunch surface is overclaiming.

### Outputs

Bounded relaunch anchor guidance, recurrence support notes, witness trace
writeback mappings into existing memory objects, reviewed closeout recall
landings, quest owner-surface refs, generated or example ref updates, and
validator requirements.

### Must not claim

- dispatch or tier escalation authority
- runtime retry budgets, rebuild policy, or live scratchpad storage
- actor role rights, handoff permissions, or identity continuity
- eval proof, adoption verdicts, or quality scoring
- playbook scenario choreography or campaign acceptance
- a new `return_memory` object family
- owner acceptance, source truth, or current truth by implication

### Validation

Use the validation lane in [AGENTS](AGENTS.md#validation).

### Next route

Route recurrence doctrine to `Agents-of-Abyss`, rights and handoff policy to
`aoa-agents`, scenario return play to `aoa-playbooks`, dispatch behavior to
`aoa-sdk`, runtime stores and retry loops to `abyss-stack`, proof to
`aoa-evals`, and source acceptance to the owning repository.

## Owner Boundary

Recurrence support remains a memo mechanic until a stronger owner decides the
route, runtime retry, proof, role right, scenario return, or source acceptance.
Memo can preserve what helps a route return; it cannot decide that return.

## Growth Posture

Future work should add stricter recurrence-support examples or validators only
when repeated route-return evidence proves a stable contract. Do not widen this
package into route dispatch, runtime state, or identity-continuity doctrine.
